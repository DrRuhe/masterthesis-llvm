IR Blob Analysis
----------------
The IR-dumping plugin embeds a serialized LLVM bitcode snapshot of the TU
as a read-only data blob registered at startup via clang_runtime_specializer_register_blob_v2.

.rodata section (IR blob):       93,944 bytes  (91.7 KB)
  As % of total file overhead:    93,944 / 133,720 = 70.2%
  As % of with-plugin file size:  93,944 / 141,776 = 66.3%

Extra .text from LLVM/CRS API header inlines pulled in by the plugin:
  3,475 bytes (3.4 KB) — these are LLVM inline methods (IRBuilder, ORC thread-safe
  wrappers, CallInst::Create, etc.) needed by the JIT wrapper generated at compile
  time. In a linked binary most of these are COMDAT-deduplicated across TUs.

Notes
-----
1. The dominant overhead source is the embedded IR bitcode blob (~92 KB for this
   single small kernel TU).  The blob size scales with TU complexity.

2. The extra ~3.5 KB .text overhead from LLVM header inlines is largely
   COMDAT-deduplicated at link time — in a multi-TU binary this cost is paid once
   per unique inline instantiation, not once per TU.

3. The without-plugin build still compiles with the CRS header included (for the
   function signature), so the 23 B .text and 241 B .rodata present in the
   without-plugin object are CRS error-class type-info stubs, not kernel code.

4. Measurement flags: -O2 (not -O3) for a conservative baseline.  The build
   system uses -O3; at -O3 the kernel .text without plugin would be comparable
   but the IR blob size is the same (it is generated before optimisation).
